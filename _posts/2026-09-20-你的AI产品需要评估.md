## 缘起

我很多年前就开始和语言模型打交道，当时带队做了 [CodeSearchNet](https://github.com/github/CodeSearchNet)，算是 GitHub Copilot 的前身。从那时到现在，我见过很多做 LLM 产品的路子，有成的，也有不成的。不成的那些，几乎总能追溯到同一个病根：**没有建立起扎实的评估系统。**

要知道你的 AI 产品到底行不行，光靠"感觉一下"（vibe check）是不够的——它有用，但远远不够。你需要[针对用户实际任务定制的产品评估](https://hamel.dev/blog/posts/evals-faq/what-are-llm-evals.html)，它衡量的东西和通用模型基准（benchmark）完全不是一回事。

这篇文章讲的是我对"AI 产品的好评估系统长什么样"的思考。

## 快速迭代 == 成功

和软件工程一样，做 AI 能不能成，取决于你迭代得有多快。你必须有一套流程和工具来做三件事：

- 评估质量（比如：测试）。
- 调试问题（比如：记日志、查数据）。
- 改变系统的行为（提示词工程、微调、写代码）。

**很多人只盯着第三件事，结果他们的 LLM 产品永远停在 demo 阶段，再也上不去。**<sup>[1]</sup> 三件事都做好，才能形成一个良性循环，把优秀的 AI 产品和平庸的区分开来（下面的图就是这个循环的可视化）。

把评估流程打通之后，其他一切都会变得容易。这和软件工程里的测试很像：前期要投入，但长期回报巨大。

为了让这篇文章落到实处，我会拿一个真实案例来讲，我们在其中搭了一套能快速改进的系统。我会把重点放在评估上，因为它是最关键的一环。

## 案例：Lucy，一个房地产 AI 助手

[Rechat](https://Rechat.com/) 是一个 SaaS 应用，房地产从业者可以在里面做各种事：管理合同、搜索房源、制作创意素材、安排预约等等。Rechat 的核心主张是：所有事在一个地方搞定，不用在一堆工具之间来回切换。

[Rechat 的 AI 助手 Lucy](https://Rechat.com/ai/) 是一个典型的 AI 产品：一个对话界面，让你不必再点点点、敲敲敲、到处找菜单。Lucy 早期靠提示词工程进展飞快。但随着 Lucy 覆盖的功能面越来越大，AI 的表现停滞了。症状包括：

- 修好一种失败模式，另一种就冒出来，像在打地鼠。
- 除了"感觉一下"，几乎看不到 AI 在各项任务上到底表现如何。
- 提示词越写越长、越来越难驾驭，试图覆盖无数边界情况和示例。

## 评估的三个层级

严格、系统的评估是整个系统里最重要的部分。这也是为什么"评估与筛选"（Eval and Curation）在图中央用黄色高亮出来。你的大部分时间都应该花在让评估更扎实、更顺畅上。

评估有三个层级需要考虑：

- 第一层：单元测试
- 第二层：模型评估与人工评估（包括调试）
- 第三层：A/B 测试

成本上，第三层 > 第二层 > 第一层。这决定了你执行它们的节奏和方式。比如，我通常每次改代码都跑第一层评估，第二层按固定节奏跑，第三层只在产品有重大变化之后才跑。另外，在进入基于模型的测试之前，先把第一层测试攻下一大块会很有帮助，因为后面的层级要花更多的功夫和时间。

至于什么时候引入哪一层测试，没有严格的公式。你要在"尽快拿到用户反馈"、"管理用户感知"和"AI 产品的目标"之间找平衡。这和做任何产品都得做的权衡没什么本质不同。

### 第一层：单元测试

LLM 的单元测试就是断言（assertion），和你在 [pytest](https://docs.pytest.org/en/8.0.x/) 里写的一样。和普通单元测试不同的是，你要把这些断言组织好，让它们能用在单元测试之外的地方，比如数据清洗，以及模型推理时的自动重试（用断言报错来纠偏）。关键在于：这些断言要跑得快、跑得便宜，这样你开发应用的时候每次改代码都能跑一遍。如果你想不出该写什么断言，就去认真审视你的 trace 和失败模式。另外，别不好意思用 LLM 帮你头脑风暴断言！

#### 第一步：写有边界的测试

思考单元测试最有效的方式，是把你的 LLM 覆盖的范围拆成一个个功能（feature）和场景（scenario）。举个例子，Lucy 有个功能是查找房源，可以拆成下面这些场景：

**功能：房源查找**

待测功能是一个函数调用，响应用户查找房源的请求，比如"帮我找加州圣何塞三居室以上、200 万美元以内的房源"。

LLM 把它转成一个查询，去 CRM 里执行。然后断言验证返回的结果数量是否符合预期。我们的测试套件里有三条用户输入，分别触发下面三种场景，各自执行对应的断言（为了便于说明，这里做了大幅简化）：

| 场景 | 断言 |
|------|------|
| 只有一条房源匹配用户查询 | `len(listing_array) == 1` |
| 多条房源匹配用户查询 | `len(listing_array) > 1` |
| 没有房源匹配用户查询 | `len(listing_array) == 0` |

还有一些通用测试，不针对任何特定功能。比如下面这个通用测试的代码，确保输出里没有暴露 UUID：

```javascript
const noExposedUUID = message => {
  // Remove all text within double curly braces
  const sanitizedComment = message.comment.replace(/\{\{.*?\}\}/g, '')

  // Search for exposed UUIDs
  const regexp = /[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}/ig
  const matches = Array.from(sanitizedComment.matchAll(regexp))
  expect(matches.length, 'Exposed UUIDs').to.equal(0, 'Exposed UUIDs found')
}
```

CRM 返回给 LLM 的结果里有些字段不该展示给用户，比如每条记录关联的 UUID。我们的提示词告诉 LLM 不要输出 UUID，然后用一个简单的正则来断言 LLM 的回复里确实没有 UUID。

**Rechat 有几百个这样的单元测试。用户不断挑战 AI，产品不断演进，我们就根据在数据里观察到的新失败持续更新它们。** 在迭代 AI 系统（做提示词工程、改进 RAG 等等）的时候，这些单元测试是快速拿到反馈的关键。很多人在产品成熟之后会"长大"到不再依赖单元测试，转向其他层级的评估，但千万不要跳过这一步！

#### 第二步：造测试用例

要测这些断言，你得生成测试用例，也就是能触发所有待测场景的输入。我经常用 LLM 来合成这些输入。比如下面是 Rechat 用来为"创建并查询联系人"功能生成合成输入的一条提示词：

```
Write 50 different instructions that a real estate agent can give to his assistant to create contacts on his CRM. The contact details can include name, phone, email, partner name, birthday, tags, company, address and job.

For each of the instructions, you need to generate a second instruction which can be used to look up the created contact.

. The results should be a JSON code block with only one string as the instruction like the following:

[
  ["Create a contact for John (johndoe@apple.com)",
  "What's the email address of John Smith?"]
]
```

用上面的提示词，我们能生成这样的测试用例：

```
[
    [
        'Create a contact for John Smith (johndoe@apple.com) with phone number 123-456-7890 and address 123 Apple St.',
        'What\'s the email address of John Smith?'
    ],
    [
        'Add Emily Johnson with phone 987-654-3210, email emilyj@email.com, and company ABC Inc.',
        'What\'s the phone number for Emily Johnson?'
    ],
    [
        'Create a contact for Tom Williams with birthday 10/20/1985, company XYZ Ltd, and job title Manager.',
        'What\'s Tom Williams\' job title?'
    ],
    [
        'Add a contact for Susan Brown with partner name James Brown, and email susanb@email.com.',
        'What\'s the partner name of Susan Brown?'
    ],
…
]
```

对每个测试用例，我们先执行第一条用户输入来创建联系人，再执行第二条查询去取回这个联系人。如果 CRM 返回的结果不是恰好一条，就说明创建或查询环节出了问题。我们还可以顺带跑通用断言，比如验证回复里没有 UUID。随着你通过人工评估和调试观察到更多数据，这些测试必须持续更新。要点是：让它们尽可能刁钻，同时又能代表用户与系统的真实交互。

你不需要等生产数据到手才能测试系统。你可以对用户会怎么用你的产品做出有根据的猜测，然后生成合成数据。也可以先放一小批用户进来，用他们的实际用法来修正你的合成数据生成策略。判断你写的测试和断言好不好，有一个信号：模型很难全部通过。这些失败模式之后就会变成你能用微调等技术去解决的问题。

顺带一提，和传统单元测试不同，你不一定需要 100% 的通过率。通过率是一个产品决策，取决于你愿意容忍多少失败。

#### 第三步：定期跑测试并跟踪结果

编排第一层测试的方式有很多。Rechat 一直在用 CI 基础设施（GitHub Actions、GitLab Pipelines 之类）来执行这些测试。不过这部分工作流的工具还很新，变化很快。

我的建议是：选你的技术栈里摩擦最小的方式来编排测试。除了跑测试之外，你还要跟踪测试结果随时间的变化，才能看出自己有没有进步。如果你用 CI，应该把指标连同测试和提示词的版本一起收集到 CI 系统之外，方便分析和跟踪。

我建议从简单的做起，直接用你现有的分析系统来可视化测试结果。比如 Rechat 就用 Metabase 来跟踪 LLM 测试结果随时间的变化。下面是 Rechat 用 [Metabase](https://www.metabase.com/) 搭的一个看板截图：

![Rechat 用 Metabase 搭的测试看板]({{ '/images/your-ai-product-needs-evals/02-metabase.png' | relative_url }})

这张截图展示了某个特定错误（黄色部分）在 Lucy 中的出现频率，左边是我们修复之前，右边是修复之后。

### 第二层：人工评估与模型评估

在第一层测试打好扎实基础之后，你就可以进入其他形式的验证，去覆盖那些光靠断言测不出来的东西。做人工评估和基于模型的评估，有一个前提：先把 trace 记下来。

#### 记录 trace

trace 这个概念在软件工程里存在很久了，指的是对一连串事件的记录，比如一次用户会话，或者一个请求在分布式系统中流转的过程。换句话说，tracing 就是把日志按逻辑分组。在 LLM 的语境下，trace 通常指你和 LLM 的一次对话。比如一条用户消息、接着一条 AI 回复、再接着一条用户消息，这就是一个 trace。

记录 LLM trace 的方案越来越多。<sup>[2]</sup> Rechat 用的是 [LangSmith](https://www.langchain.com/langsmith)，它会记录 trace，并以人类可读的方式呈现，还带一个交互式 playground 方便迭代提示词。有时候记录 trace 需要你在代码里做埋点。Rechat 当时在用 [LangChain](https://www.langchain.com/)，它会自动把 trace 事件记到 LangSmith。下面是它看起来的样子：

![LangSmith 中的 trace 界面]({{ '/images/your-ai-product-needs-evals/03-langsmith.png' | relative_url }})

我挺喜欢 LangSmith 的，它不要求你用 LangChain，而且直观、好用。不管你选哪个方案，搜索、过滤和阅读 trace 都是必备功能。我发现有些工具连这些基础功能都没做对！

#### 看你的 trace

**你必须把看数据这件事的所有摩擦都消除掉。** 这意味着要用贴合你业务领域的方式来呈现 trace。我经常发现[自己动手做一个数据查看和标注工具](https://hamel.dev/notes/llm/finetuning/04_data_cleaning.html)效果更好，因为可以把我需要的所有信息集中到一屏上。以 Lucy 为例，要理解 AI 干了什么，我们得看很多信息源（trace 日志、CRM 等等）。这正是需要消除的那种摩擦。对 Rechat 来说，这意味着在工具里加上这些信息：

- 正在评估的是哪个工具（功能）和哪个场景。
- 这条 trace 来自合成输入还是真实用户输入。
- 用于在不同工具和场景组合之间切换的过滤器。
- 指向当前记录在 CRM 和 trace 日志系统中对应条目的链接。

我做过的每个项目，都会为它搭一个这种工具的不同变体。有时候我甚至需要把另一个应用嵌进来，才能看到用户交互到底长什么样。下面是我们为评估 Rechat 的 trace 搭的工具截图：

![为 Rechat 搭的 trace 评估工具]({{ '/images/your-ai-product-needs-evals/04-langfree.png' | relative_url }})

还有一个针对 Lucy 的特殊设计：我们注意到很多失败都出在 LLM 最终输出里的小错误（格式、内容等等）。于是我们决定让最终输出可以由人来编辑，这样就能顺手筛选、修正数据，用于后续微调。

这类工具用 Gradio、Streamlit、Panel 或 Shiny 这些轻量前端框架，一天之内就能搭出来。上面展示的那个工具是用 Shiny for Python 做的。另外还有像 [Lilac](https://www.lilacml.com/) 这样的工具，用 AI 做语义搜索和过滤，在调试某个问题、想找一批相似数据点的时候非常好用。

我通常一开始只把样本标成"好"或"坏"。我发现打分或者更细粒度的评级，管理起来比二元标注麻烦得多。有一些高级技巧能让人工评估更高效或更准确（比如[主动学习](https://en.wikipedia.org/wiki/Active_learning_(machine_learning))、[共识投票](https://supervisely.com/blog/labeling-consensus/)等），但我建议从简单的开始。最后，和单元测试一样，你应该把人工评估的结果组织起来做分析，看看自己是否在随时间进步。

后面会讲到，这些标注好的样本有三个用处：衡量系统质量、验证自动评估、为微调筛选高质量的合成数据。

##### 该看多少数据？

经常有人问我该看多少数据。刚开始的时候，能看多少就看多少。我通常至少会把所有测试用例生成的 trace 和用户产生的 trace 全部读一遍。**你永远不能停止看数据，天下没有免费的午餐。** 不过随着时间推移，你可以更多地采样，减轻负担。<sup>[3]</sup>

#### 用 LLM 做自动评估

很多厂商想卖给你一些工具，声称能让人不用再看数据。但让人定期至少评估一部分 trace 样本，是个好主意。我经常发现"正确性"在某种程度上是主观的，你必须让模型和人对齐。

你应该跟踪基于模型的评估和人工评估之间的相关性，以此决定自己能在多大程度上依赖自动评估。此外，收集标注者解释"为什么这么判"的点评（critique），你就能通过提示词工程或微调来迭代评估模型，让它向人靠拢。不过在对齐评估模型这件事上，我更倾向于用提示词工程。

我很喜欢用 Excel 这种低技术含量的方案来迭代模型评估与人工的对齐。举个例子，在另一个涉及[自然语言查询生成器](https://www.honeycomb.io/blog/introducing-query-assistant)的项目里，我每隔几天就把下面这样的表格发给同事 Phillip 打分。表格里包含这些信息：

- **model response**：LLM 给出的预测。
- **model critique**：由另一个（通常更强的）LLM 针对上述预测写的点评。
- **model outcome**：点评模型给 `model response` 打的二元标签，"好"或"坏"。

然后 Phillip 填入他自己版本的同样信息，也就是他的点评、结论和期望的回复，每次 25 到 50 条（下图中以 "phillip_" 为前缀的列）：

![用于对齐模型评估与人工评估的表格]({{ '/images/your-ai-product-needs-evals/05-spreadsheet.png' | relative_url }})

有了这些信息，我就能迭代点评模型的提示词，让它随时间逐渐与 Phillip 充分对齐。这个过程同样可以在表格里用很低技术含量的方式跟踪：

![记录对齐尝试的表格]({{ '/images/your-ai-product-needs-evals/06-score.png' | relative_url }})

这张截图是一个表格，我们在里面记录了让模型评估向人工评估者对齐的历次尝试。

关于基于模型的评估，几条通用建议：

- 用你负担得起的最强模型。要把一样东西点评到位，往往需要高级推理能力。相比生产环境用的模型，你通常可以在点评输出时用一个更慢、更强的模型。
- 基于模型的评估是你大问题里的一个元问题。你必须维护一个迷你评估系统来跟踪它的质量。我有时会在这个阶段微调一个模型（但我尽量不这么做）。
- 把模型评估者和人对齐之后，你还得继续定期做练习，监控模型与人的一致性。

> **重要提示：关于把一致率当作指标**
>
> 在这个例子里，我们用模型和人工评估者之间的一致率（agreement），是因为我们的数据集大致是均衡的（约 50% 的样本是失败案例）。但一般来说不建议直接用原始一致率，在类别不均衡时它会产生误导。你通常应该分别衡量[精确率和召回率](https://developers.google.com/machine-learning/crash-course/classification/accuracy-precision-recall)，才能更准确地了解评判模型的对齐程度。

做出一个好的评估模型，我最喜欢的一点是：它的点评可以用来筛选高质量的合成数据。这一点后面会提到。

### 第三层：A/B 测试

最后，做 A/B 测试来确认你的 AI 产品确实在推动你想要的用户行为或结果，总是件好事。LLM 的 A/B 测试和其他类型产品的 A/B 测试没有太大差别。想深入了解 A/B 测试，我推荐读 [Eppo 的博客](https://www.geteppo.com/blog)（作者是我以前的同事，A/B 测试领域的顶尖高手）。

这个阶段可以先放一放，等你准备充分、确信 AI 产品适合给真实用户看了再做。这一层评估通常只适合比较成熟的产品。

### 评估 RAG

除了评估整个系统，你还可以评估 AI 的子组件，比如 RAG。评估 RAG 超出了本文的范围，可以看 [Jason Liu 的这篇文章](https://jxnl.github.io/blog/writing/2024/02/28/levels-of-complexity-rag-applications/)进一步了解。

## 评估系统免费解锁超能力

除了让你迭代得更快，评估系统还解锁了微调和调试的能力，能把你的 AI 产品带上一个新台阶。

### 微调

Rechat 通过微调解决了很多光靠提示词工程解决不了的失败模式。**微调最适合学习语法、风格和规则，而 RAG 这类技术则负责给模型提供上下文或最新的事实。**

微调 99% 的工作量都在于组装覆盖你 AI 产品功能面的高质量数据。但如果你有一套像 Rechat 那样扎实的评估系统，你就已经拥有了一台强大的数据生成与筛选引擎！关于微调的过程，我会在以后的文章里展开。<sup>[4]</sup>

#### 数据合成与筛选

为了说明为什么有了评估系统之后，数据筛选和合成几乎是免费的，考虑这样一个场景：你想为前面提到的房源查找功能创建更多微调数据。首先，你可以用 LLM 配上这样的提示词来生成合成数据：

```
Imagine if Zillow was able to parse natural language. Come up with 50 different ways users would be able to search listings there. Use real names for cities and neighborhoods.

You can use the following parameters:

Output should be a JSON code block array. Example:

[
"Homes under $500k in New York"
]
```

这和造测试用例的练习几乎一模一样！接下来你可以用第一层和第二层测试，把没通过断言的数据、以及点评模型认为有误的数据过滤掉。你还可以用现有的人工评估工具去看 trace，为微调数据集筛选样本。

### 调试

当你收到一条投诉、或看到一个与 AI 产品有关的错误时，你应该能快速调试它。如果你有一套扎实的评估系统，你手上已经有了：

- 一个可以搜索、过滤的 trace 数据库。
- 一组能帮你标记错误和不良行为的机制（断言、测试等）。
- 日志搜索与导航工具，帮你找到错误的根因。比如，问题可能出在 RAG、代码里的 bug，或者模型本身表现不佳。
- 针对错误做出修改、并快速验证修改是否有效的能力。

一句话：评估所需的基础设施和调试所需的基础设施，重叠度极高。

## 结语

评估系统会形成一个飞轮，让你迭代得飞快。做 AI 产品的人几乎总是卡在这一环上。希望这篇文章能给你一些关于如何搭建评估系统的直觉。几条要记住的要点：

- 消除看数据的**所有**摩擦。
- 保持简单。别去买花哨的 LLM 工具，先用手头有的。
- 如果你没在看大量数据，那你就做错了。
- 别依赖通用评估框架来衡量你的 AI 的质量。要为你的具体问题建一套专门的评估系统。
- 写大量测试，并且频繁更新。
- LLM 可以帮你打通评估系统的搭建。比如用 LLM 来：
  - 生成测试用例、编写断言
  - 生成合成数据
  - 点评和标注数据，等等
- 把评估基础设施复用到调试和微调上。

如果你想真正掌握 AI 评估，我和 Shreya Shankar 一起开了一门完整的课程：[AI Evals For Engineers & PMs](https://maven.com/parlance-labs/evals)。这门课会持续更新最新的技术。
