过去一年，我们与各行各业的数十个团队合作，帮他们构建基于大语言模型（LLM）的智能体。一个反复出现的现象是：做得最好的团队，用的往往不是复杂的框架或专门的库，而是简单、可组合的模式。

> _注：本文所描述的工具生态自 2024 年 12 月以来已有不少变化。想了解我们目前的做法，请参阅 [Claude Managed Agents 是如何构建的](https://www.anthropic.com/engineering/managed-agents) 与 [Managed Agents 文档](https://platform.claude.com/docs/en/managed-agents/overview)。_

本文分享我们在服务客户和自己动手构建智能体的过程中学到的东西，并给开发者一些构建高效智能体的实用建议。

## 什么是智能体？

"智能体"（Agent）这个词有好几种定义。有的客户把它理解为完全自主的系统：长时间独立运行，调用各种工具来完成复杂任务。也有人用它来指那些更受约束的实现，按照预先定好的流程一步步执行。在 Anthropic，我们把这些变体统称为**智能体系统**（agentic systems），但在架构上会明确区分**工作流**（workflow）和**智能体**（agent）：

*   **工作流**：LLM 和工具按照预先写好的代码路径被编排起来。
*   **智能体**：LLM 自己动态决定流程和工具的使用方式，对"怎么完成任务"保有控制权。

下文会详细展开这两类系统。附录一（"智能体的实际应用"）会介绍两个客户从中获得显著价值的领域。

## 什么时候该用（以及不该用）智能体

用 LLM 做应用时，我们的建议是：先找最简单的方案，只在确有必要时才增加复杂度。这有时意味着根本不需要构建智能体系统。智能体系统通常是拿延迟和成本去换更好的任务表现，你得想清楚这笔交易在什么情况下划算。

当复杂度确实有必要时：对于定义清晰的任务，工作流能提供可预测性和一致性；而当你需要灵活性、需要模型在大规模场景下自行决策时，智能体是更好的选择。不过对多数应用来说，把单次 LLM 调用配上检索和上下文示例做好优化，通常就够了。

## 什么时候用框架，以及怎么用

有很多框架能让智能体系统更容易实现，比如：

*   [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)；
*   AWS 出的 [Strands Agents SDK](https://strandsagents.com/latest/)；
*   [Rivet](https://rivet.ironcladapp.com/)，一个拖拽式的图形化 LLM 工作流构建器；
*   [Vellum](https://www.vellum.ai/)，另一个用于构建和测试复杂工作流的图形化工具。

这些框架把调用 LLM、定义和解析工具、串联多次调用这类标准的底层工作都简化了，上手确实容易。但它们往往会多加几层抽象，把底层真正的提示词和模型响应遮住，调试起来更困难。它们也容易诱使你在本可以更简单的地方堆复杂度。

我们建议开发者一开始直接用 LLM 的 API：很多模式几行代码就能实现。如果一定要用框架，请确保你理解它底下的代码。对框架内部机制的错误假设，是客户出问题的常见原因。

一些示例实现可参考我们的 [cookbook](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。

## 基础构件、工作流与智能体

这一节介绍我们在生产环境中见到的智能体系统常见模式。先从最基础的构件——增强型 LLM——讲起，然后逐步加大复杂度，从简单的组合式工作流一直讲到自主智能体。

### 基础构件：增强型 LLM

智能体系统最基本的构件，是一个配备了检索、工具、记忆等增强能力的 LLM。我们当前的模型已经能主动运用这些能力：自己生成搜索查询、挑选合适的工具、决定哪些信息需要保留。

![图：增强型 LLM]({{ '/images/building-effective-agents/01-augmented-llm.png' | relative_url }})

_图：增强型 LLM_

实现时我们建议重点关注两件事：一是把这些能力针对你的具体场景做定制；二是确保它们给 LLM 提供一个简单、文档完备的接口。实现这些增强的方式很多，其中一种是用我们最近发布的 [Model Context Protocol](https://www.anthropic.com/news/model-context-protocol)，开发者只需一个简单的[客户端实现](https://modelcontextprotocol.io/tutorials/building-a-client#building-mcp-clients)，就能接入一个持续壮大的第三方工具生态。

本文余下部分默认每一次 LLM 调用都具备这些增强能力。

### 工作流：提示词链（Prompt chaining）

提示词链把任务拆成一串步骤，每次 LLM 调用处理上一步的输出。你可以在任意中间步骤加入程序化检查（即图中的"gate"），确保流程没有跑偏。

![图：提示词链工作流]({{ '/images/building-effective-agents/02-prompt-chaining.png' | relative_url }})

_图：提示词链工作流_

**适用场景：** 任务能干净利落地拆成若干固定子任务时，这种工作流最合适。它的核心思路是用延迟换准确率：让每次 LLM 调用只做一件更容易的事。

**提示词链有用的例子：**

*   先生成营销文案，再把它翻译成另一种语言。
*   先写文档大纲，检查大纲是否符合特定标准，再按大纲写正文。

### 工作流：路由（Routing）

路由先对输入做分类，再把它导向专门的后续任务。这种工作流能做到关注点分离，让你为每类输入写更有针对性的提示词。没有它的话，针对一类输入做的优化很可能会拖累另一类输入的表现。

![图：路由工作流]({{ '/images/building-effective-agents/03-routing.png' | relative_url }})

_图：路由工作流_

**适用场景：** 路由适合那些存在明显不同类别、分开处理效果更好的复杂任务，前提是分类本身能做准——无论是靠 LLM，还是靠更传统的分类模型或算法。

**路由有用的例子：**

*   把不同类型的客服咨询（一般问题、退款请求、技术支持）分别导向不同的下游流程、提示词和工具。
*   把简单、常见的问题交给 Claude Haiku 4.5 这类更小、更省钱的模型，把困难、少见的问题交给 Claude Sonnet 4.5 这类能力更强的模型，兼顾效果与成本。

### 工作流：并行化（Parallelization）

有些任务可以让多个 LLM 同时处理，再用程序把输出汇总起来。这种工作流叫并行化，主要有两种形态：

*   **分段（Sectioning）**：把任务拆成彼此独立的子任务并行执行。
*   **投票（Voting）**：同一个任务跑多遍，获得多样化的输出。

![图：并行化工作流]({{ '/images/building-effective-agents/04-parallelization.png' | relative_url }})

_图：并行化工作流_

**适用场景：** 当拆出来的子任务能并行以提速，或者需要多个视角、多次尝试来提高结果置信度时，并行化很有效。对于需要兼顾多个考量点的复杂任务，让每个考量点由单独一次 LLM 调用来处理，通常效果更好，因为每次调用都能把注意力集中在一个具体方面。

**并行化有用的例子：**

*   **分段**：
    *   实现安全护栏：一个模型实例处理用户请求，另一个同时筛查其中是否有不当内容或请求。这通常比让同一次 LLM 调用既做护栏又给核心回答效果更好。
    *   自动化评估 LLM 表现：每次 LLM 调用只评估模型在某个提示词上表现的一个方面。
*   **投票**：
    *   审查一段代码有没有安全漏洞：用几个不同的提示词分别审查，发现问题就标记出来。
    *   判断某段内容是否不当：用多个提示词评估不同方面，或设置不同的投票阈值，以平衡误报和漏报。

### 工作流：编排者—工作者（Orchestrator-workers）

在编排者—工作者工作流中，一个中心 LLM 动态拆解任务，把子任务分派给多个工作者 LLM，最后再把结果综合起来。

![图：编排者—工作者工作流]({{ '/images/building-effective-agents/05-orchestrator-workers.png' | relative_url }})

_图：编排者—工作者工作流_

**适用场景：** 这种工作流适合那些你无法预知需要哪些子任务的复杂任务。以编程为例，需要改多少个文件、每个文件怎么改，很可能都取决于具体任务。它在拓扑上和并行化很像，但关键区别在于灵活性：子任务不是预先定义好的，而是由编排者根据具体输入临场决定。

**编排者—工作者有用的例子：**

*   每次都要对多个文件做复杂修改的编程产品。
*   需要从多个来源搜集并分析信息、找出相关内容的搜索任务。

### 工作流：评估者—优化者（Evaluator-optimizer）

在评估者—优化者工作流中，一次 LLM 调用负责生成回答，另一次负责评估并给出反馈，两者循环往复。

![图：评估者—优化者工作流]({{ '/images/building-effective-agents/06-evaluator-optimizer.png' | relative_url }})

_图：评估者—优化者工作流_

**适用场景：** 当我们有明确的评估标准、且反复迭代能带来可衡量的提升时，这种工作流尤其有效。判断是否合适有两个信号：一是当人类把反馈说清楚后，LLM 的回答确实能明显改善；二是 LLM 自己也能给出这样的反馈。这很像人类写作者打磨一篇文稿时反复修改的过程。

**评估者—优化者有用的例子：**

*   文学翻译：译者 LLM 一开始可能抓不住某些细微之处，但评估者 LLM 能给出有价值的批评。
*   需要多轮搜索和分析才能收集到全面信息的复杂搜索任务，由评估者来决定是否还需要继续搜。

### 智能体

随着 LLM 在几项关键能力上日渐成熟——理解复杂输入、进行推理和规划、可靠地使用工具、从错误中恢复——智能体正逐步进入生产环境。智能体的工作起点，要么是人类用户的一条指令，要么是一段交互式讨论。任务明确之后，智能体便独立规划和执行，中途可能会回头向人类索取更多信息或请求判断。执行过程中至关重要的一点，是智能体每一步都要从环境中获取"事实依据"（比如工具调用结果或代码执行结果）来评估进展。智能体可以在检查点或遇到阻碍时暂停，等待人类反馈。任务通常在完成时结束，但加上停止条件（比如最大迭代次数）以保持可控，也是很常见的做法。

智能体能处理复杂的任务，但它的实现往往很直接：本质上就是一个 LLM 在循环中根据环境反馈使用工具。因此，把工具集及其文档设计得清晰、周到，就变得极为重要。附录二（"给工具做提示词工程"）会展开讲工具开发的最佳实践。

![图：自主智能体]({{ '/images/building-effective-agents/07-autonomous-agent.png' | relative_url }})

_图：自主智能体_

**什么时候用智能体：** 智能体适合开放性问题——所需步骤数很难或根本无法预测，也没法硬编码一条固定路径。LLM 可能要运行很多轮，你必须对它的决策有一定程度的信任。智能体的自主性使它非常适合在可信环境里把任务规模做大。

自主性也意味着更高的成本，以及错误层层叠加的风险。我们建议在沙箱环境里做充分测试，并配上合适的护栏。

**智能体有用的例子：**

以下例子来自我们自己的实现：

*   一个解决 [SWE-bench 任务](https://www.anthropic.com/research/swe-bench-sonnet)的编程智能体，需要根据任务描述修改许多文件；
*   我们的 ["computer use" 参考实现](https://github.com/anthropics/anthropic-quickstarts/tree/main/computer-use-demo)，让 Claude 操作电脑来完成任务。

## 组合与定制这些模式

这些构件不是教条，只是一些常见模式，开发者可以按不同场景自由塑造和组合。和任何 LLM 功能一样，成功的关键在于衡量效果、迭代实现。再强调一遍：**只有**在复杂度能被证明确实改善了结果时，才考虑增加复杂度。

## 总结

在 LLM 领域取得成功，靶心不是造出最精巧的系统，而是造出**适合**你需求的系统。从简单的提示词开始，用全面的评估去优化它，只有当简单方案确实不够用时，才引入多步骤的智能体系统。

实现智能体时，我们尽量遵循三条核心原则：

1.  保持智能体设计的**简单**。
2.  优先保证**透明**：把智能体的规划步骤明确展示出来。
3.  通过完善的工具**文档与测试**，精心打造智能体与计算机之间的接口（ACI，agent-computer interface）。

框架能帮你快速起步，但迈向生产环境时，别犹豫去削减抽象层、用基础组件重新搭建。遵循这些原则，你做出的智能体不仅强大，而且可靠、可维护，值得用户信赖。

## 附录一：智能体的实际应用

与客户合作的过程中，我们发现了两个特别有前景的 AI 智能体应用领域，它们很好地印证了上文各模式的实用价值。这两个应用都说明了一点：智能体最能创造价值的任务，往往同时具备这些特征——既需要对话又需要行动、有清晰的成功标准、能形成反馈闭环、并且融入了有意义的人工监督。

### A. 客户支持

客户支持把大家熟悉的聊天机器人界面和工具集成带来的增强能力结合在一起，天然适合更开放的智能体，原因如下：

*   支持对话本身就是一种会话流，同时又需要访问外部信息、执行外部操作；
*   可以集成工具来拉取客户数据、订单历史和知识库文章；
*   退款、更新工单这类操作可以用程序完成；
*   成功与否可以用用户定义的"问题已解决"来清晰衡量。

已有多家公司用"按成功解决数计费"的定价模式证明了这条路走得通——只对成功解决的问题收费，这本身就是对智能体效果的信心。

### B. 编程智能体

软件开发领域展现出了 LLM 功能的巨大潜力，能力从代码补全一路演进到自主解决问题。智能体在这里尤其有效，因为：

*   代码方案可以通过自动化测试来验证；
*   智能体可以拿测试结果当反馈，迭代方案；
*   问题空间定义清晰、结构良好；
*   输出质量可以客观衡量。

在我们自己的实现中，智能体如今已经能仅凭 pull request 的描述，就解决 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准里真实的 GitHub issue。不过，自动化测试虽能帮助验证功能，人工审查对于确保方案符合更广泛的系统要求，仍然不可或缺。

## 附录二：给工具做提示词工程

不管你在构建哪种智能体系统，工具很可能都是其中的重要一环。[工具](https://www.anthropic.com/news/tool-use-ga)让 Claude 得以与外部服务和 API 交互：你在我们的 API 里精确指定工具的结构和定义，Claude 在回复时如果打算调用某个工具，就会在 API 响应里带上一个[工具调用块](https://docs.anthropic.com/en/docs/build-with-claude/tool-use#example-api-response-with-a-tool-use-content-block)。工具的定义和规格值得投入和整体提示词同等的提示词工程精力。这篇简短的附录讲的就是怎么给工具做提示词工程。

同一个操作往往有多种表达方式。比如修改文件，可以写一个 diff，也可以把整个文件重写一遍；结构化输出，可以把代码放在 markdown 里，也可以放在 JSON 里。在软件工程里，这类差异只是表面形式，彼此之间可以无损转换。但对 LLM 来说，某些格式写起来要难得多。写 diff 意味着在写出新代码之前，就得先在块头里知道有多少行会变；把代码写进 JSON（相比 markdown）则需要额外转义换行和引号。

关于工具格式的选择，我们的建议是：

*   给模型足够的 token 去"思考"，别让它把自己写进死角。
*   格式尽量贴近模型在互联网文本中自然见过的样子。
*   确保没有额外的格式"负担"，比如要精确数清几千行代码，或者要对自己写的代码做字符串转义。

一条经验法则：想想人们在人机界面（HCI）上投入了多少心思，然后计划在**智能体**—计算机界面（ACI）上投入同样多的心思。以下是一些具体想法：

*   站在模型的角度想。光看描述和参数，这个工具怎么用是一目了然的，还是得仔细琢磨？如果你得琢磨，模型大概也得琢磨。一份好的工具定义通常包含使用示例、边界情况、输入格式要求，以及与其他工具的清晰边界。
*   参数名和描述怎么改能让事情更显而易见？把它当作给团队里的初级开发者写一份出色的 docstring。当你有很多相似的工具时，这一点尤其重要。
*   测试模型怎么用你的工具：在我们的 [workbench](https://console.anthropic.com/workbench) 里跑大量示例输入，看模型会犯什么错，然后迭代。
*   给你的工具做[防呆设计（Poka-yoke）](https://en.wikipedia.org/wiki/Poka-yoke)：调整参数，让出错变得更难。

在为 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 构建智能体的过程中，我们花在优化工具上的时间其实比花在整体提示词上的还多。举个例子，我们发现智能体一旦离开根目录，用相对路径的工具就容易出错。解决办法是把工具改成始终要求绝对路径——改完之后，模型用起来一次都没错过。
