借助 [Model Context Protocol（MCP）](https://modelcontextprotocol.io/docs/getting-started/intro)，LLM 智能体可以接上数以百计的工具，去解决真实世界里的任务。问题是：怎样才能让这些工具发挥出最大的效用？

这篇文章分享我们在各类智能体 AI 系统中提升性能时，最管用的一些技巧[^1]。

先讲怎么做：

- 搭建并测试工具的原型；
- 借助智能体，为工具设计并运行全面的评估；
- 和 Claude Code 这样的智能体协作，自动提升工具的表现。

最后总结一路走来提炼出的几条写好工具的关键原则：

- 选对要实现的工具（以及不该实现的工具）；
- 用命名空间给工具划清功能边界；
- 让工具给智能体返回有意义的上下文；
- 优化工具响应的 token 效率；
- 对工具描述和规格做提示词工程。

_有了评估，就能系统地衡量工具的表现；再让 Claude Code 对照这份评估，自动优化你的工具。_

## 什么是工具？

在计算机领域，确定性系统只要输入相同，每次都会给出相同的输出；而**非确定性**系统——比如智能体——即使起始条件完全一样，也可能给出不同的回应。

传统意义上写软件，其实是在确定性系统之间订立契约。比如调用 `getWeather("NYC")`，无论调用多少次，它都会以完全相同的方式去取纽约的天气。

工具则是一种新型软件，它体现的是确定性系统与非确定性智能体之间的契约。用户问"今天要不要带伞？"，智能体可能会调用天气工具，可能直接凭常识回答，也可能先反问一句你在哪儿。偶尔，它还会产生幻觉，甚至压根搞不懂某个工具该怎么用。

这意味着，为智能体写软件，需要从根本上换一种思路：不能再像给其他开发者或系统写函数、写 API 那样去写工具和 [MCP 服务器](https://modelcontextprotocol.io/)，而是要专门为智能体来设计。

我们的目标，是借助工具让智能体能用各种行之有效的策略去解决各式各样的任务，从而扩大它们能发挥作用的范围。好在根据我们的经验，对智能体最"顺手"的工具，往往对人来说也出奇地直观。

## 怎么写工具

这一节讲怎么和智能体协作，既写出给它们用的工具，也把这些工具改得更好。第一步，快速搭个工具原型，在本地测一测。接着，跑一轮全面的评估，作为衡量后续改动的基准。然后和智能体一起，反复"评估—改进"，直到它们在真实任务上表现出色。

### 搭建原型

不亲自上手，你很难预料哪些工具智能体用着顺手、哪些不顺手。所以先快速搭一个原型。如果你用 [Claude Code](https://www.anthropic.com/claude-code) 来写工具（说不定一次就能写成），最好把工具要依赖的软件库、API 或 SDK（可能也包括 [MCP SDK](https://modelcontextprotocol.io/docs/sdk)）的文档一并交给 Claude。对 LLM 友好的文档，通常能在官方文档站点上以扁平的 `llms.txt` 文件形式找到（这是[我们 API 的](https://docs.anthropic.com/llms.txt)）。

把工具封装成[本地 MCP 服务器](https://modelcontextprotocol.io/docs/develop/connect-local-servers)或[桌面扩展](https://www.anthropic.com/engineering/desktop-extensions)（DXT），就能在 Claude Code 或 Claude 桌面应用里接入并测试。

要把本地 MCP 服务器接入 Claude Code，运行 `claude mcp add <name> <command> [args...]`。

要把本地 MCP 服务器或 DXT 接入 Claude 桌面应用，分别前往 `Settings > Developer` 或 `Settings > Extensions`。

也可以把工具直接传给 [Anthropic API](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview) 调用，以编程方式做测试。

自己动手测一测，找出那些还不顺手的地方。再收集用户反馈，对工具要支撑的使用场景和提示词建立起直觉。

### 运行评估

接下来，你需要跑一轮评估，量一量 Claude 用你的工具用得怎么样。先基于真实使用场景生成大量评估任务。我们建议找一个智能体来帮你分析结果、判断工具该怎么改。完整流程可以参考我们的[工具评估 cookbook](https://platform.claude.com/cookbook/tool-evaluation-tool-evaluation)。

_我们内部 Slack 工具在留出测试集上的表现_

#### 生成评估任务

有了早期原型，Claude Code 就能快速摸清你的工具，造出几十组提示词与响应。提示词应当取材于真实的使用场景，基于真实的数据源和服务（比如内部知识库和微服务）。我们建议不要用过于简单、流于表面的"沙盒"环境，它们的复杂度不足以给工具做压力测试。好的评估任务可能需要多次工具调用——甚至几十次。

下面是一些好的任务：

- 下周和 Jane 约个会，讨论我们最新的 Acme Corp 项目。附上上次项目规划会的纪要，再订一间会议室。
- 客户 ID 9182 反映一次购买被扣了三次款。找出所有相关的日志记录，并判断是否还有其他客户受到同一问题影响。
- 客户 Sarah Chen 刚提交了取消申请。准备一个挽留方案。弄清楚：（1）对方为什么要走；（2）什么样的挽留方案最有吸引力；（3）提出方案之前，有哪些风险因素需要我们注意。

下面是一些较弱的任务：

- 下周和 jane@acme.corp 约个会。
- 在支付日志里搜索 `purchase_complete` 和 `customer_id=9182`。
- 找出客户 ID 45892 提交的取消申请。

每条评估提示词都应该配一个可验证的响应或结果。验证器可以简单到拿标准答案和采样响应做字符串精确比对，也可以高级到请 Claude 来评判。别用过于严格的验证器，因为格式、标点或另一种同样正确的说法这类无关紧要的差异，就把正确的回答判错。

对每一组提示词与响应，你还可以选择性地标注出你预期智能体在解题时会调用哪些工具，借此衡量评估中智能体是否真的理解了每个工具的用途。不过，正确解决一个任务可能有多条可行路径，所以尽量别把策略规定得太死，也别对某种策略过拟合。

#### 运行评估

我们建议直接调用 LLM API，以编程方式运行评估。用简单的智能体循环（一个 `while` 循环，里面交替进行 LLM API 调用和工具调用）：每个评估任务一个循环。每个评估智能体只拿到一条任务提示词和你的那套工具。

在评估智能体的系统提示词里，我们建议要求它们不仅输出结构化的响应块（用于验证），还要输出推理块和反馈块。要求它们把这些内容放在工具调用块和响应块**之前**输出，可能会触发思维链（CoT）行为，从而提升 LLM 的有效智力。

如果你用 Claude 跑评估，可以打开[交错思考](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking)（interleaved thinking），"开箱即用"地获得类似效果。这能帮你探究智能体为什么调用或不调用某些工具，并指出工具描述和规格中具体该改进的地方。

除了顶层的准确率，我们还建议收集其他指标，比如单次工具调用和单个任务的总耗时、工具调用总次数、token 总消耗量，以及工具报错情况。跟踪工具调用能揭示智能体常走的工作流，也能提示哪些工具有合并的空间。

#### 分析结果

智能体是发现问题的好帮手，从相互矛盾的工具描述，到低效的工具实现，再到令人困惑的工具 schema，它们都能给出反馈。但要记住：智能体在反馈和回答里**没说**的东西，往往比说了的更重要。LLM 并不总是[言如其意](https://www.anthropic.com/research/tracing-thoughts-language-model)。

观察智能体在哪里卡住、在哪里犯迷糊。通读评估智能体的推理和反馈（或 CoT），找出不顺手的地方。再翻看原始对话记录（包括工具调用和工具响应），捕捉那些智能体在 CoT 里没有明说的行为。要读出字里行间的意思；别忘了，你的评估智能体并不一定知道正确答案和正确策略。

分析工具调用的各项指标。大量冗余的工具调用，可能说明分页或 token 上限参数需要调到合适的大小；大量因参数无效导致的报错，可能说明工具需要更清晰的描述或更好的示例。我们上线 Claude 的[网页搜索工具](https://www.anthropic.com/news/web-search)时就发现，Claude 会多此一举地在工具的 `query` 参数后面加上 `2025`，导致搜索结果出现偏差、性能下降（后来我们通过改进工具描述，把 Claude 引回了正轨）。

### 与智能体协作

你甚至可以让智能体替你分析结果、改进工具。只要把评估智能体的对话记录拼接起来，粘贴进 Claude Code 就行。Claude 很擅长分析对话记录，也擅长一次性重构一大批工具——比如在做出新改动时，确保工具的实现和描述依然前后一致。

事实上，这篇文章里的大部分建议，都来自我们用 Claude Code 反复优化内部工具实现的过程。我们的评估建立在内部工作空间之上，还原了内部工作流的复杂度，包括真实的项目、文档和消息。

我们依靠留出测试集来确保没有对"训练用"的评估过拟合。这些测试集表明，即便是"专家级"的工具实现——无论是研究员手写的，还是 Claude 自己生成的——我们仍能从中榨出额外的性能提升。

下一节，我们来分享从这个过程中学到的一些东西。

## 写好工具的原则

这一节把我们的经验提炼成几条写好工具的指导原则。

### 为智能体选对工具

工具不是越多越好。我们常见的一个错误是：工具只是简单地把现有的软件功能或 API 端点包一层——不管这些工具适不适合智能体。原因在于，智能体与传统软件有着不同的"可供性"（affordance），也就是说，它们感知自己能用这些工具做哪些事的方式不一样。

LLM 智能体的"上下文"是有限的（一次能处理的信息量有上限），而计算机内存既便宜又充裕。拿在通讯录里找联系人这个任务来说。传统软件程序可以高效地存储并逐条处理联系人列表，一个个检查过去。

但如果 LLM 智能体用的工具返回了**全部**联系人，然后它得一个 token 一个 token 地读下去，那就是把有限的上下文空间浪费在无关信息上了（想象一下，你在通讯录里找人，却从第一页开始逐页往下读——也就是暴力搜索）。更好、也更自然的做法（对智能体和人都一样）是先翻到相关的那一页（比如按字母顺序找）。

我们建议先针对少数几个影响大的特定工作流，构建几个经过深思熟虑的工具，让它们和你的评估任务对得上，再从这里逐步扩展。在通讯录这个例子里，你可以考虑实现 `search_contacts` 或 `message_contact` 工具，而不是 `list_contacts` 工具。

工具可以整合功能，在底层处理**多个**独立的操作（或 API 调用）。比如，工具可以给响应补充相关的元数据，或者把经常串在一起的多步任务放进一次工具调用里完成。

下面是一些例子：

- 与其分别实现 `list_users`、`list_events` 和 `create_event` 工具，不如考虑实现一个 `schedule_event` 工具，由它来查空闲时间并安排日程。
- 与其实现 `read_logs` 工具，不如考虑实现一个 `search_logs` 工具，只返回相关的日志行和少量上下文。
- 与其分别实现 `get_customer_by_id`、`list_transactions` 和 `list_notes` 工具，不如实现一个 `get_customer_context` 工具，一次性汇总某个客户近期的所有相关信息。

确保你构建的每个工具都有清晰、独特的用途。工具应该让智能体能像人一样拆分并解决任务（前提是人能访问同样的底层资源），同时减少原本会被中间输出占掉的上下文。

工具太多或者功能重叠，也会让智能体分心，没法走更高效的路子。仔细、有取舍地规划要构建（或不构建）哪些工具，回报会非常可观。

### 给工具加上命名空间

你的 AI 智能体可能会接入几十个 MCP 服务器、上百种不同的工具——其中包括其他开发者写的。当工具功能重叠或用途模糊时，智能体就会搞不清该用哪个。

命名空间（把相关工具归到共同的前缀下）有助于在大量工具之间划清界限；有些 MCP 客户端默认就会这么做。比如，按服务（如 `asana_search`、`jira_search`）和按资源（如 `asana_projects_search`、`asana_users_search`）给工具加命名空间，能帮助智能体在合适的时机选对工具。

我们发现，命名空间用前缀还是后缀，对工具使用评估的结果有不小的影响。效果因 LLM 而异，我们建议你根据自己的评估结果来选命名方案。

智能体可能会调错工具，可能用错误的参数调对了工具，可能调用的工具太少，也可能错误地处理工具响应。有选择地实现那些名字能反映任务自然拆分方式的工具，既能减少载入智能体上下文的工具数量和工具描述，又能把一部分智能体的计算从上下文里卸下来，交还给工具调用本身。这能降低智能体整体出错的风险。

### 让工具返回有意义的上下文

同样的道理，工具实现应当注意只给智能体返回高信号的信息。它们应该优先考虑上下文相关性，而不是灵活性，并且避开底层的技术标识符（比如 `uuid`、`256px_image_url`、`mime_type`）。`name`、`image_url`、`file_type` 这类字段，更有可能直接影响智能体后续的行动和回答。

比起晦涩的标识符，智能体处理自然语言的名称、术语或标识符时也要得心应手得多。我们发现，仅仅是把任意的字母数字 UUID 解析成语义更明确、更好理解的语言（甚至只是一套从 0 开始编号的 ID 方案），就能减少幻觉，显著提高 Claude 在检索任务上的精确度。

在某些情况下，智能体可能需要既能处理自然语言输出、又能处理技术标识符输出的灵活性，哪怕只是为了触发后续的工具调用（比如 `search_user(name='jane')` → `send_message(id=12345)`）。你可以在工具里暴露一个简单的 `response_format` 枚举参数来同时支持两者，让智能体自己决定工具返回 `"concise"`（简洁）还是 `"detailed"`（详细）的响应（见下图）。

你还可以加入更多格式来获得更大的灵活性，类似 GraphQL 那样可以精确挑选想要哪些信息。下面是一个用来控制工具响应详略程度的 ResponseFormat 枚举示例：

```
enum ResponseFormat {
   DETAILED = "detailed",
   CONCISE = "concise"
}
```

甚至连工具响应的结构——比如 XML、JSON 还是 Markdown——都会影响评估表现：没有放之四海而皆准的方案。这是因为 LLM 是用下一个 token 预测来训练的，面对和训练数据相匹配的格式往往表现更好。最优的响应结构会因任务和智能体的不同而差别很大。我们建议你根据自己的评估来选择最合适的响应结构。

### 优化工具响应的 token 效率

优化上下文的质量很重要，但优化工具响应返回给智能体的上下文的**数量**也同样重要。

对于任何可能占用大量上下文的工具响应，我们建议组合使用分页、范围选择、过滤和/或截断，并配上合理的默认参数值。在 Claude Code 里，我们默认把工具响应限制在 25,000 个 token 以内。我们预计智能体的有效上下文长度会随时间增长，但对上下文高效的工具的需求不会消失。

如果你选择截断响应，一定要用有帮助的说明来引导智能体。你可以直接鼓励智能体采用更省 token 的策略，比如在知识检索任务中，用多次小而精准的搜索代替一次大而宽泛的搜索。同样，如果工具调用报错（比如在输入校验阶段），你可以对错误响应做提示词工程，清楚地传达具体、可操作的改进建议，而不是丢给它一个看不懂的错误码或堆栈回溯。

工具的截断提示和错误响应，可以把智能体引向更省 token 的工具使用方式（使用过滤或分页），也可以给出格式正确的工具输入示例。

### 对工具描述做提示词工程

现在来说提升工具效果最有效的方法之一：对工具描述和规格做提示词工程。由于这些内容会被载入智能体的上下文，它们合在一起，就能把智能体引向高效的工具调用行为。

写工具描述和规格时，想想你会怎么向团队里的新同事介绍这个工具。考虑那些你可能默认对方知道的背景——专门的查询格式、小众术语的定义、底层资源之间的关系——然后把它们明确写出来。清楚地描述预期的输入和输出（并用严格的数据模型加以约束），避免歧义。尤其是输入参数，命名要毫不含糊：与其叫 `user`，不如叫 `user_id`。

有了评估，你就能更有把握地衡量提示词工程的效果。哪怕只是对工具描述做些小小的打磨，也可能带来巨大的提升。在我们对工具描述做了精确的打磨之后，Claude Sonnet 3.5 在 [SWE-bench Verified](https://www.anthropic.com/engineering/swe-bench-sonnet) 评估中取得了业界领先的成绩，错误率大幅下降，任务完成率显著提升。

更多关于工具定义的最佳实践，可以参阅我们的[开发者指南](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#best-practices-for-tool-definitions)。如果你在为 Claude 构建工具，我们也建议读一读工具是如何被动态载入 Claude 的[系统提示词](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#tool-use-system-prompt)的。最后，如果你在为 MCP 服务器写工具，[工具注解](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)（tool annotations）可以标明哪些工具需要开放世界访问，或者会做出破坏性的修改。

## 展望

要为智能体构建高效的工具，我们需要把软件开发实践的重心，从可预测的、确定性的模式，转向非确定性的模式。

通过本文描述的这套迭代式、评估驱动的流程，我们发现了让工具成功的一些一贯规律：高效的工具定义明确、用意清晰，对智能体的上下文用得审慎，能在各种工作流中组合使用，并能让智能体直观地解决真实世界的任务。

未来，智能体与世界交互的具体机制还会不断演进——从 MCP 协议的更新，到底层 LLM 本身的升级。只要用系统化、评估驱动的方法来改进智能体的工具，我们就能确保：随着智能体越来越强，它们所用的工具也会与之一同进化。

## 译者注

- **Agent** 译作"智能体"，**agentic systems** 译作"智能体系统"，与本站《构建高效的 AI 智能体》保持一致。
- **Ergonomic** 原意是"符合人体工学的"，这里译作"顺手"，取其"用起来舒服、不别扭"的意思。
- **Affordance** 译作"可供性"，这是设计心理学里的通行译法，指一个对象让使用者"看出来能拿它做什么"的特性。作者借它说明：同一个工具，在智能体眼里和在传统程序眼里，"能做的事"并不一样。
- **Held-out test set** 译作"留出测试集"，指评估时专门留出来、不参与迭代优化的那部分数据，用来检验是否过拟合。
- **Namespacing** 译作"命名空间"，**prompt-engineering** 作动词时译作"做提示词工程"。
- **Interleaved thinking** 译作"交错思考"，指模型在多次工具调用之间穿插进行思考。
- 工具名、参数名、枚举值等代码标识符一律保留英文原样。
